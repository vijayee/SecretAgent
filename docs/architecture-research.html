What we are building, and why this document exists

SecretAgent is a portable C library — a Pony-style actor runtime over a durable WaveDB store with a loadable persona — plus the desktop agent that runs it. It is built by dissecting the best part of four production agent harnesses and keeping only their essence (patterns, not code). This document is the groundwork for that dissection: a verified description of how each reference harness processes a prompt (entry → context assembly → model call → tool execution → response), the components and data flows involved, and an honest critique of each architecture against our goals: legibility of state, portability (could it be a clean C library?), loop correctness, efficient context handling, and visible communication while working.

Every loop step, component, and dataflow edge below was extracted from repository sources by a mapping agent and re-verified by a second agent that re-opened the cited files (invented or mismatched claims were killed). Critiques are code-grounded; items the agents could not confirm from source are marked unverified.

  • The system prompt is data, not a side channel: it travels only as system/message surface events (SystemPromptProjection.project in packages/core/agent-loop/src/runtime-context.ts:88-103), where the first prompt reserves surface node 0, capable routes append in-history updates, incapable/new-series routes consolidate at the head and empty later nodes. Critique

Strengths

  • Legibility of state is the best I have seen: the durable append-only log IS the actor state, and every model request is a pure fold over it. buildRequest derives messages from session.deriveMessages() + session.toolHistory() and deep-freezes them (packages/core/agent-loop/src/agent.ts:669-686); no plugin can feed the model unlogged content without first committing an event. Session maintains incremental, cursor-tracked folds (headerFold/headFoldSeq, contextFold, toolHistory, deriveMessages with contentGeneration invalidation — packages/core/session/src/index.ts:775-881), so per-step reads cost O(new events). This is exactly the 'isolated actor + durable log' shape and it ports to C + WaveDB almost directly.
  • The pending-input mailbox is itself durable, not in-memory: every inbox mutation is an 'agent/inbox/spliced' event validated incrementally by a strict fold (bounds checks, duplicate message-id rejection) in inboxProjectionDefinition (packages/core/agent-loop/src/inbox.ts:27-65). claim() (inbox.ts:109-114) removes the claimed batch by logging the splice. A crashed actor restarts with its mailbox intact, derived from the same log.
  • Crash/replay discipline is real engineering, not aspiration: aborted or skipped tool calls always produce ordered synthetic 'tool call aborted before dispatch' results so the transcript stays tool-call/tool-result balanced (packages/core/agent-loop/src/tool-calls.ts:238-260); step failure recovers pending tool results via ToolCallRecovery (agent.ts:331-353); turn/end is appended in a finally block with a full reason union (aborted/error/max-tokens/blocked/completed) — agent.ts:385; and packages/core/session/src/repair.ts adds deterministic open-turn closers over a persisted truncated log with cause-specific, model-facing wording (TOOL_NOT_STARTED / TOOL_OUTCOME_UNKNOWN with idempotency guidance). The JSONL backend does true crash work: header+first batch temp-write/fsync/link()/unlink publish (never rename), directory fsync, truncate of a crash tail, monotonic length enforcement (packages/session/session-persistence-jsonl/src/index.ts:1175-1223, 1308-1364; packages/session/session-persistence-jsonl/src/storage.ts:170-175).
  • The tool-call scheduler is a compact, disciplined state machine: exclusive calls form barriers, parallel calls run in a bounded rolling pool (maxParallelToolCalls), results commit strictly in model order via commitReady, and later calls are re-classified before start so registry changes can create a barrier mid-group (packages/core/agent-loop/src/tool-calls.ts:122-247). This is a small, portable essence — an array of slots plus an ordered commit cursor.
  • Compaction is log surgery, not in-place history rewriting: a compaction run replaces a selected surface span with one summary node via surfaceOp replace markers (shadowedSeqs), which bumps surface.contentGeneration and starts a new request series; deriveMessages rebuilds lazily (packages/core/session/src/index.ts:860-881, packages/compaction/compaction/src/index.ts). Compaction as an event over the same log is highly portable and keeps the audit trail intact.
  • Context-efficiency choices are deliberate and good: the dynamic runtime-context snapshot is committed as a durable user message ONLY when its text changed (RuntimeContextProjection, packages/core/agent-loop/src/runtime-context.ts:152-163; committed at agent.ts:419-423), avoiding per-step duplicate context blocks; the request envelope is re-logged only when canonicalHeader differs (change detection vs requestHeader baseline, agent.ts:612-634); request headers/series semantics give context-window changes and compaction explicit sequence meaning (agent.ts:615-633).
  • Driver concurrency discipline is small and correct-in-spirit: a 3-variant Phase state machine {idle, maintenance, running} with wake-latching — a wake arriving during maintenance or an aborted activity is latched as wakeRequested and replayed at convergence, never lost (agent.ts:154-235, 390-395); max-tokens is sticky so later steps cannot downgrade the turn outcome (agent.ts:341).

Weaknesses

  • Durability is advisory, not commit-based — the single biggest tension with a WaveDB-backed actor model. Session.append pushes to an in-memory log and synchronously notifies observers (packages/core/session/src/index.ts:754-772); disk is written by a background listener observing 'session/event' (storage.ts:535) with batched, deadline-driven drains ('pending', 'flush', 'deadline-driven drain failure' in storage.ts). The loop proceeds past an append (and through full model calls) on events that are not yet on disk; a crash loses the undrained prefix and resume 'repairs' it by synthesizing outcomes for tool calls whose results were lost (repair.ts), and sessions created but not yet flushed 'never existed if the process crashes before that' (persistence index.ts:243). Correct for a JS CLI's latency budget, but a port should be append-commit-then-proceed.
  • Replay is plugin-dependent — the log is 'open' but its interpretation is not self-contained. SessionMessageProjection lets a plugin rewrite the CONTENT of existing model-visible messages post hoc (packages/core/session/src/surface.ts:35-46), and the store documents that 'Disposing the contribution makes sessions that used it refuse further derivation' (packages/core/session/src/index.ts:946-949). A restored session whose projecting plugin is absent cannot be derived at all. 'Model-visible means logged' is weaker than advertised: what the model SAW can be rewritten by a projection while the original event text stays in the file, and future replay depends on which plugins are loaded.
  • Framework gravity: 61 packages, 2052 TS files, ~351k lines of source for one agent harness (repo metrics). The core loop is genuinely small (agent.ts 688 lines, inbox 244, tool-calls 290), but the Cordis substrate (vendor/cordis), ScopedLayers, ~8 distinct waterfalls (agent/pre-step, agent/request, agent/request-error, agent/turn-stopping, system-prompt/assemble, tools/pre-execute/execute/post-execute), three projection systems (sessionProjections, SessionMessageProjection, surface projections) and patch/profile composition (apps/cli/src/profile-boot.ts) is enormous indirection the C port cannot and should not carry.
  • Hidden ambient context: tool execution and subagent drivers discover the owning agent through AsyncLocalStorage requireInitiator() (packages/core/agent/src/index.ts:248-344; tool-calls.ts:68 ctx.agents.requireInitiator()). This is implicit thread-local state threaded through the hot path — the opposite of explicit actor message passing, invisible at call sites, and a pattern that must be explicitly parameterized (owner id in the message) in C, where it silently works 'because the ALS happens to be set'.
  • Defensive-language overhead baked into the hot loop: every step deepFreezes the canonical header, structuredClones the seed config, deep-freezes every derived message into a WeakSet (frozenMessages, agent.ts:119-120, 655-686), and every append runs snapshotJsonValue full-tree validation on data + surface metadata (packages/core/session/src/index.ts:732-739). Immutability-by-freezing is JS scaffolding whose 'essence' (immutability by ownership, single writer) a C runtime gets structurally; the machinery itself is dead weight.
  • The step() hot path interleaves ~8 async seams per model call (pre-step waterfall → assemble waterfall → request waterfall → prepareCall → per-chunk emit → request-error waterfall → turn-stopping serial), and failure containment relies on convention: a throwing plugin inside any waterfall aborts the turn, and error paths must thread AggregateErrors manually ('Step failed and its pending tool results could not be recorded' agent.ts:351; 'Assistant stream failed and its durable settlement was rejected' agent.ts:479). Correctness is subtle rather than obvious — e.g. the code comments admit reentrant cancel can occur during a splice observer (agent.ts:156) and whenIdle() must re-read activityDone in a loop (agent.ts:237-242).
  • Log growth is one-way: failed stream attempts are durably recorded as assistant/attempt events (agent.ts:467-493) and assistant messages embed their full compact provider stream record (agent.ts:451-465, 522-528); neither is surface-eligible, so compaction cannot shadow them — a long agent session's log file accumulates every retries' stream debris forever (only generation files are immutable, never repacked).

Failure modes

  • Crash mid-turn with a drained-but-unflushed write: tool calls whose side effects actually executed get resume-synthesized 'outcome is unknown — retry only if read-only or idempotent' results (repair.ts CLOSER_TEXT). The design acknowledges this loss is possible; with an at-least-once background writer it is a structural, not exceptional, window — exactly what the WaveDB backing in our runtime should close.
  • Session restore fails to derive at all if a previously used message-projection plugin is absent (registerMessageProjection contract, packages/core/session/src/index.ts:943-950); combined with projections being allowed to rewrite visible message content (surface.ts:35-46), two processes with different plugin sets can legitimately derive different 'model-visible history' from the same byte-identical log.
  • A buggy or hostile plugin in any waterfall breaks the loop: agent/pre-step can reject or rewrite queued input (agent.ts:276-282), agent/request rewrites route config (agent.ts:576-579), and a thrown error inside these propagates through the turn boundary as an opaque 'UNKNOWN' errorChain entry (agent.ts:375-381). No resource isolation exists between plugin and loop — one bad plugin can wedge or corrupt any agent in the process, since all agents share one Cordis context tree and JS heap.
  • Reentrancy hazards around synchronous notification: session.append invokes observers synchronously while the 'appending' reentry guard is armed (packages/core/session/src/index.ts:741-743, 754-772), and inbox splice observers can call cancel() mid-splice (agent.ts:156). The code handles these by convention and v8-ignore pragmas; the C port must make this ordering explicit or it will be re-broken.
  • whenIdle() correctness rests on a promise identity race (agent.ts:237-242) and runGroup on Promise.race over in-flight slots with commit interleaving (tool-calls.ts:221-231); both are microtask-ordering-dependent subtleties that do not translate mechanically to a C scheduler and have thin test coverage relative to their trickiness.
  • Log and derivative-rebuild blowup in long sessions: every failed retry durably persists a full compact stream record (assistant/attempt, agent.ts:469-492) that no compaction pass can remove, and contentGeneration bumps force a full deriveMessages rebuild — a session with heavy retries and periodic compaction pays O(surface) rebuilds repeatedly with no repack path.

Steal — essences for our portable runtime

  • THE essence — 'log is the state': one append-only event log per actor; every outbound model/tool request is derived from folds over that log (deriveMessages/toolHistory with incremental per-fold cursors and a contentGeneration invalidation counter — packages/core/session/src/index.ts:775-881). In C: WaveDB per-actor log + a small projection table (fold state, consumed-seq cursor, generation counter). This is the cleanest portable core; everything else hangs off it.
  • Durable inbox-as-log: mailbox = fold over splice events with bounds/duplicate-id validation (inbox.ts:27-65) plus claim() semantics (next-step batch first, one queued turn). Gives a restartable actor mailbox for free from the same store, no separate queue file.
  • Turn/step lifecycle envelope + crash repair layer: turn/start, step/start|end with step/end always written even on failure (agent.ts:354-357), turn/end carrying a full reason union (aborted/error/max-tokens/blocked/completed), and a pure, deterministic openTurnClosers() that synthesizes results and boundaries over any truncated log (packages/core/session/src/repair.ts), including cause-specific, model-facing wording telling the model about idempotency. Directly implementable as a couple hundred lines of C over WaveDB; this is what makes resume safe.
  • Tool-call scheduling state machine: exclusive-barrier + bounded-parallel-pool, commit strictly in model order, synthetic results for unstarted calls on abort, results linked to their call seq via sourceEventSeqs (packages/core/agent-loop/src/tool-calls.ts). Port as an explicit array-of-slots machine; it needs no async runtime.
  • Compaction as log surgery, not in-place surgery: a summary message replaces (shadows) a contiguous node span; derivatives see the change via a generation bump and rebuild. In C, compaction is just another log event type — extremely valuable for long-lived embedded agents.
  • Driver discipline patterns: wake latching during maintenance/abort (wakeDriver, agent.ts:214-235 — a wake is never lost, it is replayed at convergence); sticky turn outcomes (max-tokens never downgraded); one phase at a time with wakeRequested as the single latch flag. Simple, portable invariants expressible as a small phase-union.
  • Envelope-only logging with change detection: canonical request header comparison so identical config is not re-logged each step (buildRequest, agent.ts:612-634), and route metadata (model, contextWindow, systemPromptUpdate) folded into a durable request/context event that prompt projection can consult. Cheap, high-value for auditability in a C store.

This is the strongest of the four harnesses where it counts for your port: session-log-as-actor-state, the durable inbox fold, and the cause-specific crash repair are exactly the essence a portable C actor runtime over WaveDB should be built from, implemented with unusually rigorous discipline. But it is a framework, not a library — 61 packages of Cordis indirection, ambient AsyncLocalStorage attribution, and plugin-owned history rewriting are the price of its flexibility and are precisely what you should not carry across. Port the log/projection/inbox/repair/scheduler quintet as first-class C constructs with commit-before-proceed durability; discard the plugin architecture, the projection-extensible replay path, and the self-rolled persistence backend (WaveDB replaces all 1725 lines of it).

Distinctive design facts

  • Single-tool RLM design: createAllToolDefinitions returns only {ipython} (tools/index.ts 52–55) and the default active tool set is ['ipython'] (agent-session.ts 10889); reading/editing files, bash, skills, MCP, and subagents are all Python code in a persistent kernel with a dill snapshot protocol — per-variable 16 MiB / 256 MiB aggregate caps (kernel/shared.ts 41–46) with an oversized-variable prune (pruneOversizedVariables: shared.ts 300, repl-manager.ts 1616, ipython.ts 396) used on compaction.
  • Typed host-request bridge instead of many tools: Python calls `await rlm.spawn(...)` or `goal.*` and the call ships as a host_request stdio event; ReplKernelManager.handleHostRequest dispatches on a string type to handlers built in _createKernelHostHandlers (agent-session.ts 10941–11082) and answers with host_reply carrying the same id (repl-manager.ts 1354), so a cell can block on admission without stalling other kernel work.
  • Spawn is admission-only: rlm.spawn validates, enforces RLM_DEPTH < RLM_MAX_DEPTH (agent-session.ts 12611), resolves model/thinking (failing rather than substituting, 12630–12644), creates a sub-<8hex> child dir (11179), admits into a parent-scoped registry, and returns an RLMSpawnHandle immediately — child answers never return via this path, and child token usage is folded into the parent assistant turn via durable child_usage_attributed transcript entries (appendChildUsageAttribution at 12698; docs/rlm-runtime.md '## Child Execution' section).
  • Session-input admission is a first-class state machine: every prompt source (user, steering, follow-up, cron/heartbeat, agent messages, bash-completion notices, goal/autonomous continuations) becomes a QueuedSessionAction with delivery classes and commit fences, pumped by _pumpSessionInputs only at safe quiescence points (agent-session.ts 6879–7308); the action model (delivery policies, lanes, priorities) lives in session-action-store.ts, and steering vs follow-up/continuation queues also exist inside the loop itself (agent-loop.ts getSteeringMessages 314 / getFollowUpMessages 415 / getContinuationMessages 431).
  • Continual harness keeps the base system prompt immutable and injects learned state as a fingerprinted [harness-digest] custom message re-delivered at turn commit only when harness state changed (messages.ts HARNESS_DIGEST_CUSTOM_TYPE 49 and createHarnessDigestMessage 208; agent-session.ts 7233–7245); /refine and auto-refine run an auxiliary-model review (planRefinement, refinement.ts 1231–1316, over the serialized last 80k chars at 1258; reviewAutoRefine 1331 over 40k chars at 1344) and apply small validated create/update/delete CRUD edits via the same JSON state files the Python harness.py writes (harness_state.json, refinements.jsonl), reloading from disk to avoid clobbering.

Critique

Strengths

  • The wire protocol is a genuinely portable actor-transport blueprint. Newline-JSON frames, an exact version handshake, a closed event vocabulary validated on the host side (kernel/repl-manager.ts:66-82 and 145-175 invalidProtocolFrameReason), hard per-frame payload caps (repl.py:50 _PAYLOAD_CAP, repl-manager.ts:77 MAX_PROTOCOL_LINE_CHARS), id-keyed request/reply with dedup of handled host-request ids (repl-manager.ts:205, 71), and a defined repair path for corruption. The Python side is a thin shim that 'does not call providers or implement an agent loop' (docs/rlm-runtime.md:72): all policy and persistence stay in the host. This is precisely the isolated-actor/typed-message pattern the C runtime wants, already proven across a process boundary.
  • Spawn as admission-only message passing, not RPC: rlm.spawn returns an RLMSpawnHandle 'immediately after task admission' and 'never waits for or returns the child's answer' (docs/rlm-runtime.md:30); results arrive only via explicit agent_message.send or files; progress notes are deliberately pull-only ('notes never steer the parent', rlm-runtime.ts:426-433) and rlm.collect returns snapshots on timeout instead of rejecting (rlm-runtime.ts:386-416). Parent-scoped child registry survives kernel restart and parent restore; deletion writes a durable tombstone without erasing history (docs/rlm-runtime.md:171). A clean, durable actor model: fire-and-forget spawn, explicit reply channels, pull-only status — the clearest statement of the target semantics in any of the four harnesses.
  • Input admission is a first-class, formally-checked state machine rather than scattered await logic. session-action-store.ts defines the full action lifecycle with a LEGAL_TRANSITIONS table (lines 99-108) enforced at runtime (transitionSessionAction throws on illegal moves, 114-134), rollback requires a RollbackProof proving the primary message is not durable in the transcript (126-131), and delivery splits on a single dimension: next_turn_boundary vs when_run_idle (7-20). Every submission source funnels through _pumpSessionInputs which only dispatches when an explicit 8-condition quiescence predicate passes (session-action-store.ts:canSelectSessionAction 444-455), with passivation/eviction kept as pure policy helpers (411-442). The store is nearly liftable to C as-is.
  • Fail-loud instead of fail-soft at every policy boundary: unknown rlm.spawn kwargs are rejected rather than ignored (agent-session.ts:12602-12605), an unavailable child model fails the spawn instead of silently substituting the parent model (12630-12645), unsupported thinking levels fail with the supported list. This discipline makes the single-tool surface trainable and travels to C as a convention: handlers return typed errors, never silent defaults.
  • Bounded-resource thinking is baked into the transport, not bolted on: per-execution output caps (DEFAULT_MAX_OUTPUT_CHARS, repl-manager.ts:29), 64KiB unattributed-background-output buffer (73), 2KiB spawn-cell-source cap (81), per-variable 16MiB / 256MiB aggregate snapshot caps with pruneOversizedVariables used during compaction (kernel/shared.ts:41-46, 300), budgeted stderr log rotation with write-budget accounting (285-327), and Python-side strict-dumps NaN validation protecting host framing (repl.py:105-115). Nearly every byte crossing the boundary has an owner and a cap — the right posture for a portable C library.
  • Context efficiency is handled as a durable versioned record, not prompt surgery. Learned state is materialized as a fingerprinted [harness-digest] custom message (messages.ts:49 HARNESS_DIGEST_CUSTOM_TYPE), injected at turn commit only when the harness-state fingerprint changed (agent-session.ts:7233-7245), parked rather than lost when a turn aborts (7155-7162 re-arms _harnessDigestPending), and deduplicated on reload so only the newest digest is delivered (session-manager.ts:499-535). The base system prompt stays immutable (refinements are supplemental state, docs/rlm-runtime.md:193), preserving provider prompt-cache prefixes and keeping learned state auditable as data.
  • Kernel lifecycle is written by people who have been burned: generation counters so a teardown cannot kill a newer start's kernel (repl-manager.ts:226-227, 341-420 startStale), memoized concurrent startup, orphan-process journaling so a host crash cannot leak children (orphan-process-journal.ts; PRIME_AGENT_KERNEL_OWNER_PID at repl-manager.ts:382), explicit handling of 'ready and garbage in one stdout chunk' (393-398), and a documented failure-mode table (docs/rlm-runtime.md:235-246). The defensiveness targets real hazards, not decoration.

Weaknesses

  • AgentSession is a single 15,101-line orchestration object (packages/coding-agent/src/core/agent-session.ts) owning the input pump, tool registry, system prompt, kernel host handlers, child registry, usage attribution, goals, autonomous mode, compaction, retry, and refinement. The message-passing story lives at the kernel boundary, but the host side of every actor concern (registry, mailbox, spawn, accounting) is collapsed into one process-wide mutable state. For a C port this is the critical anti-lesson: the essence (action store + typed request dispatch) is clean and separable (session-action-store.ts and rlm-runtime.ts ARE separable), but the code as written does not factor — everything mutates `this` under ad-hoc fences.
  • Concurrency safety is maintained by hand-rolled, hard-to-verify coordination rather than by an actor scheduler. The pump juggles an epoch counter (_sessionInputPumpEpoch checked at agent-session.ts:6887, 6936), DeferredSessionInputError rollback with transcript-proof reconstruction (6962-6991), a commit fence (_acquireSessionActionCommitFence, 7219-7228) plus re-entrancy checks inside the fenced closure, and promise-chained event ordering (_agentEventQueue.then at 12685). Correct, but it is imperative single-threaded-event-loop discipline over ~7 boolean quiescence flags (RuntimeActivity, session-action-store.ts:357-366) — exactly the regime that a C actor runtime with per-actor mailboxes makes structural, and exactly the regime that cannot be audited locally.
  • Durability is appendFileSync on the hot path: session-manager.ts:2018 writes each transcript entry synchronously inside _persist, invoked from message_end processing (agent-session.ts:4635-4648) — synchronous fs calls on the session thread, no batching/group commit/fsync policy, JSONL replay as the only recovery (also 961 for branch targets). Fine for a CLI; wrong as the persistence model for a portable actor runtime, where the store should be the boundary, not an event side-effect.
  • The single-threaded kernel is both pillar and straightjacket: the ipython tool is executionMode:'sequential' explicitly because 'the kernel is single-threaded' (ipython.ts:690-691), ReplKernelManager serializes all executes on one promise chain (repl-manager.ts:209-210), and a busy kernel degrades the whole turn into an interactive UI choice — wait or kill — decided inside the tool path (executeWithBusyKernelChoice, ipython.ts:606-668), where headless mode auto-cancels the model's call (choice 'cancel' when !ctx.hasUI, 610-611, 622). No preemption story at actor granularity; parallelism exists only one level up per-subagent (one LLM session per actor — a coarse, expensive unit).
  • Dill blob snapshots are the durable-state substrate for the kernel — the wrong durability model to copy: kernel-state.dill with a magic header, per-variable caps, and best-effort restore that silently drops unserializable objects (repl.py:39 _SNAPSHOT_MAGIC; kernel snapshot/restore skip-sets repl.py:53-55), while real durable state (harness_state.json, refinements.jsonl, session JSONL, child registry) lives in scattered JSON files each with its own reload-to-avoid-clobbering logic (refinement.ts, docs/rlm-runtime.md:191). A C port should put all of these INSIDE the durable store, not around it.
  • Stringly-typed dispatch with contract triplication: handleHostRequest dispatches on data.type and AgentSession builds a handler record keyed by type (agent-session.ts:10941-11082), while every handler in rlm-runtime.ts re-declares the same field validation the Python shim already did with isinstance checks (rlm/__init__.py:135-151) — three copies of each contract (Python, TS validators, docs) with no codegen, and version evolution resting on PROTOCOL_VERSION=3 exact-match that fails hard on any mismatch (repl-manager.ts:66, 399-404) instead of negotiating.
  • Context budgeting is scattered across four layers with ad-hoc truncation rather than one output-budget policy: tool-result shaping in ipython.ts (725-757 concatenating stdout/stderr/result/traceback/backgroundOutput), background-output attribution at the kernel (repl-manager.ts:220-222), digest-only-newest re-delivery in session-manager.ts (499-535), and a separate model-driven compaction pass (compaction/compaction.ts estimateTokens 230, findCutPoint 382). Each layer owns its own magic constants; a C runtime should own one budget function per boundary.

Failure modes

  • Busy-kernel wedge: one shared namespace, single-threaded kernel (repl-manager.ts:209-210) means a long-running cell blocks the whole turn; recovery is an interactive UI prompt (executeWithBusyKernelChoice ipython.ts:625-668) which headless mode auto-resolves to 'cancel' — silent abandonment of the model's action in headless operation.
  • Best-effort durability of kernel state: dill snapshot/restore drops unserializable variables and reports them; bootstrap deliberately overwrites restored handles (ipython.ts:558-567 'Revive a prior session's namespace before the bootstrap, so the bootstrap then overwrites live handles'). After a crash the model can be told state was restored that is only partially there.
  • Sync persistence + swallowed write errors: transcript writes are appendFileSync on the live session thread (session-manager.ts:2018), and child-usage attribution failures are explicitly ignored — 'a failed append must not break run settlement' with an empty catch (agent-session.ts:12698-12702) — so usage can silently drift from transcripts.
  • Protocol-corruption recovery is a full teardown path: an invalid frame triggers protocol repair, kernel discard, rebootstrap, and (unless the snapshot is the declared culprit) namespace restore (repl-manager.ts:239-255 pendingRebootstrap/pendingRestore, startupProtocolError check 393-398); one corrupting cell costs the entire kernel including in-flight background bash handles.
  • Concurrency-regime fragility at every extension point: new input sources must be threaded through the pump epochs, DeferredSessionInputError rollbacks, commit fences, and the digest-exclusion filter in parkNextTurnMessages (agent-session.ts:7155-7159) correctly or messages are delivered twice or dropped — the legibility cost of the hand-rolled concurrency regime is paid continuously, not once.
  • Spawn-name reservation leak paths: the _pendingRlmSubagentSessionNames add/release dance reserves a name pre-admission and releases it via a detached runtime task or on every failure path (agent-session.ts:12616-12656); a missed release permanently blocks that child name for the parent's lifetime.
  • Documented non-sandbox: the kernel executes model-generated Python and bash() with worker OS permissions — 'it is not a security sandbox' (docs/rlm-runtime.md:231) — a correctness/safety boundary the architecture delegates entirely to external tooling.

Steal — essences for our portable runtime

  • The admission state machine as a portable C mailbox module: messages enter a store with a lifecycle enum, a hard-coded legal-transition table, and explicit rollback with durability proof (session-action-store.ts:63-134). This is arguably the best part of all four harnesses: message *admission*, not sending, is what keeps the loop correct. The store is ~455 lines of near-pure logic — transcribe the transition table, the two delivery classes (next_turn_boundary vs when_run_idle), the pinned/user/background priority rank, priority-ordered queue insertion, and the rollback-proof check directly.
  • The framed typed-message bridge as the runtime's universal transport: newline-delimited JSON, exact version handshake, closed event vocabulary validated on every frame, request/reply paired by id, bounded frame size, deduped handled-request ids, and full-connection repair on corruption (repl-manager.ts:66-175; repl.py:152-188). This gives 'actors = isolates with typed inboxes' for free: an actor's mailbox is an id-keyed pending-request table plus an event stream over one fd — no shared memory, no callback gymnastics.
  • Admission-only spawn semantics as the actor-spawn API: spawn validates (depth cap at agent-session.ts:12611, unique child name reservation, model resolution that fails rather than substitutes), creates a per-child durable directory and registry entry, and returns a handle that never carries the child's answer; results flow only via explicit agent_message replies, pull-only progress notes, or bounded collect (rlm-runtime.ts:388-442). A production-proven supervision model mapping 1:1 onto spawn(actor)->pid with replies as messages to the parent's inbox.
  • The fingerprinted side-car persona digest: the persona prompt stays immutable; learned state is persisted as data with a state fingerprint, materialized as one bounded digest message at commit only when the fingerprint changes (agent-session.ts:7233-7245), parked-and-rearmed on abort (7155-7162), and deduplicated to newest-only on replay (session-manager.ts:499-535). This is simultaneously your loadable-persona mechanism, your context-efficiency mechanism (cache-stable system prompt), and your replay-dedup rule — one pattern, three goals.
  • Fail-loud resource policy as a single runtime concern: every boundary-crossing payload is size-capped and truncated at the source (repl.py _PAYLOAD_CAP 50, _RESULT_TEXT_CAP 47; repl-manager.ts 73-86; shared.ts pruneOversizedVariables 300). In C, bake one budget table (per-frame, per-turn, aggregate) into the frame layer so every actor gets bounded memory for free and an oversized message fails its own actor, never the runtime.
  • Generation counters for lifecycle safety: every restart bumps a generation and stale completion paths compare against it before touching state (repl-manager.ts:226-227, 341-420). Three lines of C that eliminate the classic bug of a delayed completion from a killed actor corrupting a restarted one.
  • The loop skeleton as the turn engine: outer loop = per-turn (parked-message drain, model call, tool execution, stop-checks, steering poll), inter-turn = idle-queue drain then follow-up then continuation polls, every early exit emitting a terminal event (agent-loop.ts:304-448). Small and self-contained; in C it becomes one actor running its loop over its own inbox, with shouldStopAfterTurn as the host's policy hook.

Steal-avoid / reject

  • The Python REPL kernel as the control substrate: dill snapshots, uv-bootstrapped venv (kernel/bootstrap.ts ensureKernelPython), asyncio/contextvars cell machinery, per-variable Python introspection — all CPython baggage. The essence is 'one tool that is arbitrary code in a persistent session with a typed bridge'; define your own minimal, sandboxable control surface instead of inheriting Python runtime management and best-effort object revival.
  • The 15k-line AgentSession object and its organization: do not port the file or its topology; re-home each extracted essence (action store, loop, spawn/registry, digest) into its own actor with WaveDB-owned state. Copying its structure reproduces the single-writer choke point and the epoch/fence scaffolding.
  • appendFileSync-on-hot-path persistence and JSONL-as-database (session-manager.ts:2018, 961): WaveDB is the boundary — commit at message boundaries with transactions, not synchronized file appends plus replay repair.
  • The hand-rolled async scaffolding (commit fences, pump epochs, DeferredSessionInputError, _agentEventQueue promise chains, the 7-flag RuntimeActivity gate): this is TS-event-loop glue replicating what scheduler-owned per-actor mailboxes give natively; in the C runtime, the action store's admission rules become mailbox policy enforced by the scheduler, not application code.
  • The extension/before_agent_start hook system, daemon/RPC/ACP mode plumbing, and TUI/daemon protocol versioning (daemon-protocol.ts, daemon-supervisor.ts 1924-2012): host-ecosystem glue, not runtime essence; the persona+digest pattern covers the subset you need.
  • Licensing caution: packages/* are @earendil-works/pi-agent-core / pi-ai (a pi-mono fork); even for essence-only reuse, verify the upstream license before any code-level borrowing; the Python side (prime-agent-runtime) carries the same caution.

This is likely the best source of the four for a C actor-runtime precisely because its valuable part already IS an actor system: a framed, versioned, id-keyed request/reply protocol over a pipe, admission-only spawn with durable parent-scoped registries, an explicitly-legal-transition message-admission machine, and fingerprinted durable side-state — all of which transpose almost directly onto isolated actors + WaveDB mailboxes + a loadable persona. What does not transpose is the implementation: a 15k-line single-writer orchestrator held together by epochs, fences and booleans, a CPython/dill persistence substrate, and synchronous file durability on hot paths. Port the patterns and the fail-loud, budget-everything discipline; consciously replace the kernel, the blob snapshots, and the God session with store-backed actor state and a single output-budget policy.

How a prompt becomes context

Per LLM cycle (not per turn), onyx/chat/llm_loop.py assembles the full context: (1) System message — build_system_prompt (prompt_utils.py:253) fills the editable default-persona system prompt (get_default_base_system_prompt pulls the 'default behavior' Persona row's system_prompt column via get_default_behavior_persona, falling back to DEFAULT_SYSTEM_PROMPT in onyx/prompts/chat_prompts.py:13) with {{placeholders}} (datetime, citation guidance), appends a # User Information section (basic info, org profile, company context, language, preferences, memories from UserMemoryContext), and appends tool guidance sections only for tools present this cycle type-checked by isinstance (prompt_utils.py:299-342). If persona.replace_base_system_prompt is set, the persona's system_prompt stands alone as the system message and the custom-agent prompt becomes None (llm_loop.py:967-1012). (2) The persona's custom-agent prompt (persona.system_prompt when not replacing the base) is processed by process_prompt_template and inserted as a USER message immediately before the last user message — it 'moves' with the history each turn (llm_loop.py ordering comment 597-599; onyx/chat/README.md example 105-119). (3) History — construct_message_history (llm_loop.py:405) budgets available_tokens = LLM input window minus reserved tokens minus system/custom-agent/project-file/reminder tokens, keeps history from the last user message onward (with last_n_user_messages filtering), truncates older history from the top, and inserts project/context file messages, a 'forgotten files' metadata message for files evicted from context (llm_loop.py:~540-615, so FileReaderTool can still read them), and context images attached to the last user message. (4) Tool schemas — each Tool.tool_definition() (OpenAI function format; MCPTool at tools/tool_implementations/mcp/mcp_tool.py:124 converts the MCP input schema; SearchTool exposes a 'queries' array) is passed as the `tools` argument to run_llm_step/LitellmLLM.stream_raw alongside tool_choice (AUTO, REQUIRED for forced_tool_id, NONE on the out-of-cycles or post-image-gen cycle), llm_loop.py:947-960 + ~1113-1140. (5) Reminder — a trailing reminder USER message (persona task_prompt, citation/answer-completeness reminders, open-URL or file reminders, last-cycle citation notice) from select_reminder_text (llm_loop.py:782) sits at the very end. Documents from search arrive as JSON where each result uses the key 'document' keyed to a plain number via convert_inference_sections_to_llm_string (tools/tool_implementations/utils.py:29). run_llm_step_pkt_generator translates ChatMessageSimple -> ChatCompletionMessage (translate_history_to_llm_format, incl. per-provider tool-history flattening and image caps for non-vision models) and passes the should_cache-marked prefix through the prompt-cache layer (process_with_prompt_cache, llm_step.py:699 / multi_llm.py:1572) before the LiteLLM call.

Distinctive design facts

  • Three message representations, deliberately layered: ChatMessage (DB row, onyx/db/models.py:3287) -> ChatMessageSimple (canonical in-memory model) -> ChatCompletionMessage (LLM-facing, onyx/llm/model_request) — documented in backend/onyx/chat/README.md:246-251.
  • 'Moving' context-blocks design (backend/onyx/chat/README.md:93-119): custom-agent prompt, project files and reminders are re-inserted before the most recent user message every cycle instead of living in history, because instruction-following drops when these blocks age away from the end of context.
  • Packets over return values: every level (llm_step, tools, search) communicates by emitting typed Packet objects (ReasoningStart/Delta, ReasoningDelta, AgentResponseDelta, CitationInfo, SearchToolStart, SectionEnd, OverallStop) tagged with Placement(turn_index/tab_index/model_index) through an Emitter into a shared queue that _run_models' writer thread drains while a reader tails a tee queue — the whole turn is one interleaved line-delimited-JSON stream (StreamingResponse with media_type='text/event-stream' but JSON-line payload) that also supports multi-model side-by-side comparison.
  • Tool-call history is deliberately truncated: previous-turn tool RESPONSE documents are replayed as the TOOL_CALL_RESPONSE_CROSS_MESSAGE placeholder ('This tool call completed but the results are no longer accessible.', onyx/prompts/chat_prompts.py:108) while call arguments are kept, because tool args are token-cheap and information-rich (README:78-87) — and evicted file context is compensated with a 'forgotten files' metadata message wired to FileReaderTool (llm_loop.py:~540-615).
  • Citations are a first-class runtime subsystem: a DynamicCitationProcessor interleaves with the token stream to rewrite [[1]] hyperlinks live while the loop maintains a citation num -> document id mapping (set_citation_mapping at llm_loop.py:~1154) and persists per-message citations (llm_step.py citating emission ~852-873, save_chat.py:169) — document JSON sent to the LLM uses the key 'document' to keep the model citing a plain number (README:49-64).
  • Cancellation and durability go through a cache-backend fence, not Redis specifically: the stop endpoint sets an FENCE_TTL=10-min key 'chatsessionstop_fence_<id>' via set_fence (onyx/chat/stop_signal_checker.py:23) on whatever CacheBackend is configured (Redis or Postgres, onyx/cache/factory.py:42); the drain (writer) thread polls check_stop_signal every _CANCEL_POLL_INTERVAL_S = 50 ms (process_message.py:1136), a StreamBufferWriter tees every packet to the cache so /resume-stream can replay from any pod (chat_backend.py:1297), and worker-completion, stop-button, and post-steps paths all funnel through a persist_lock-guarded _persist_model_outcome that guarantees exactly-once saving plus a single compression claim per turn (process_message.py:1241).
  • Search is an LLM-in-the-loop RAG flow, not a naive retrieval: SearchTool.run runs semantic + keyword query expansion, source-scope and time-filter decisions in parallel with the chat LLM (search_tool.py:600-660, run at 661), then fans out parallel sub-searches; expanded queries (not the model's originals) are what get replayed in history (README:84-87).

Critique

Strengths

  • Packets-over-return-values as the universal boundary: every layer (llm_step, tools, search) communicates by emitting typed Packet objects tagged with a Placement routing header through an Emitter (backend/onyx/chat/emitter.py:8-40; Packet at server/query_and_chat/streaming_models.py, Placement at placement.py). Reasoning deltas, citations, tool Start/SectionEnd, errors and OverallStop all become one interleaved, inspectable event stream, with multi-model merging by model_index and single-vs-multi model sharing one execution path (process_message.py:1159-1177). For an actor runtime this is exactly the right ESSENCE: mailbox messages with a routing header, and total communication visibility for free.
  • Deliberate three-representation message layering with a written contract: DB ChatMessage -> canonical in-memory ChatMessageSimple -> LLM-facing ChatCompletionMessage, with layer-scoped rules documented in chat/README.md:246-251 ('converted into ChatMessageSimple early and never passed deep into the flow'). The prompt renderer is a projection, not the storage of record - a clean separation that ports directly into one C struct plus a rendering function.
  • Budgeted, per-block token accounting in context assembly: construct_message_history (llm_loop.py:405-450) subtracts system-prompt, custom-agent, project-file and reminder token counts before budgeting raw history and explicitly raises on a negative budget rather than silently overflowing the context window; prompt-cacheability is a named first-class flag (system_prompt.should_cache = True, llm_loop.py:453).
  • Empirically validated, documented context-layout policy: chat/README.md:93-162 encodes the prompt-engineering invariants as design rules - the persona prompt as a movable USER message re-anchored before the last user message each cycle (ordering comment llm_loop.py:597-599), reminders pinned last, documents to the LLM keyed as a bare {"document": N} integer for citation reliability (README:47-64), and even a measured claim that moving one instruction block changes follow-rate from 30% to 90% (README:158-162).
  • Durability as a first-class seam, not an afterthought: StreamBufferWriter (chat/stream_buffer.py:64-151) is an append-only, compressed, size-capped tee with an explicit truncated flag and a stated degradation contract ('a broken cache downgrades the run to non-resumable'); the stop fence is a 10-minute TTL key over a pluggable CacheBackend (Redis or Postgres, not hardcoded Redis) at chat/stop_signal_checker.py:23-48; a dropped client resumes by cursor from any pod.
  • Exactly-once outcome persistence reasoned for crash/stop/concurrent completion: _persist_model_outcome (process_message.py:1241-1290) uses persisted[] flags plus persist_lock reachable from any thread, success/error classification, and a single compression_claimed latch per turn measured against the min input window across the turn's models (comment at process_message.py:1223-1226, min() at 1288-1289). Real concurrency correctness reasoning, written down.
  • Tool failure is data, not an escape hatch: _safe_run_single_tool (tools/tool_runner.py:118-229) converts expected and unexpected tool exceptions into an llm_facing_response string and always emits SectionEnd in success or failure - the loop never dies because a tool crashed; the model gets a consumable error string.
  • Cross-turn history compaction with a correct information-density trade: previous-turn tool responses are replaced by a TOOL_CALL_RESPONSE_CROSS_MESSAGE placeholder while call arguments are kept (README:78-87, chat_prompts.py:108), and evicted file context is compensated with a forgotten-files metadata message wired to FileReaderTool (llm_loop.py:~540-615). Args are token-cheap and information-rich - a stated, sensible heuristic.

Weaknesses

  • Threads-sharing-mutable-state, not actors - the very shape a C actor runtime should avoid. _run_models (process_message.py:1159-1240) is a hand-rolled scheduler: worker threads plus an unbounded merged_queue plus a tee queue plus a writer drain loop plus a reader generator, with per-model state spread across mutable arrays captured in closures (model_succeeded/model_errored/model_error_info/persisted, process_message.py:1214-1226) and two threading.Events (drain_done, reader_gone). Correctness rests on fragile protocol comments ('the writer is the run's lifeline... the reader can die freely', process_message.py:1234-1238) rather than on structure; ChatStateContainer itself needs a lock (chat_state.py:40-46).
  • Cancellation is advisory polling and stop is wasteful by design. The stop fence is only observed in the drain loop while the queue is empty, every 50 ms (_CANCEL_POLL_INTERVAL_S = 0.05, process_message.py:1136), and the code concedes 'The LLM loops never observe the stop signal... a worker that returns non-errored always holds a complete answer' (process_message.py:1248-1252). On stop, workers cannot be interrupted and their remaining emits are simply discarded (comment at 1230-1232) - the model runs to completion and its output is thrown away at full token cost. Cancel is checked on a wall-clock cadence rather than at loop/tool quiescence points, squandering the durable-fence idea's promise of deterministic cancel points.
  • Prompt-layout policy is prose plus scattered code, not data: the moving-context rules live in chat/README.md:93-119 while their enforcement lives in ~200 lines of llm_loop history surgery (llm_loop.py:405-615), and per-tool system-prompt guidance is selected with runtime isinstance checks (prompt_utils.py:299-342). Nothing structural prevents a new tool from silently missing guidance or a new message kind landing in the wrong slot - invariants documented but not machine-checkable.
  • Silent capability degradation in tool construction: construct_tools 'simply skips tools that are not allowed/available' (tools/tool_constructor.py:169, 255-257) with no packet and no warning surfaced into the turn - a persona referencing an unavailable tool yields an agent that silently lacks a visible behavior, violating the repo's own communication-visibility ethos.
  • Untyped sentinel soup at queue boundaries: merged_queue is Queue[tuple[int, Packet | Exception | object]] (process_message.py:1204) and the tee is Queue[Packet | StreamingError | object] (process_message.py:1236) - exceptions, sentinel objects and packets share one channel with no discriminated encoding. NullEmitter (emitter.py:43-56) silently drops packets for side-entrypoints such as the Search API, weakening the one-stream-one-truth invariant exactly where debuggability matters most.
  • Magic-constant citation namespace: concurrent citation-producing tools are assigned citation-number ranges advanced by +100 per call (tool_runner.py:232-260 region) - a +100 collision bound enforced nowhere and broken if a single tool returns more than 100 documents.
  • Budget exhaustion is a crash, not a policy: 'Not enough tokens available to construct message history' raises ValueError (llm_loop.py:449-450). A large project bundle plus a big persona system prompt on a small-window model is an error page, not a defined eviction order; the system refuses to degrade in a specified way.
  • History fidelity erosion from merged tool calls and query-expansion replay: _merge_tool_calls keeps only the first call's id when collapsing N search/web calls into one (tool_runner.py:100-110), and history records ONE ASSISTANT tool_calls array plus N TOOL_CALL_RESPONSE messages (llm_loop.py:1389-1445); combined with replaying expanded queries instead of what the model actually asked (README:84-87), history is a lossy projection that would silently poison any provider validating tool_call_id uniqueness.

Failure modes

  • Stop-button token waste: LLM loops never observe the fence (comment, process_message.py:1248-1250), so pressing Stop burns the full remaining inference stream for every running model and discards it; only the drain loop's 50 ms polling halts further tool cycles.
  • Fence availability is load-bearing: check_is_connected polls the CacheBackend every 50 ms inside the drain loop; a Redis/Postgres blip either fails the turn or (if the error is swallowed) silently disables cancellation - there is no documented degraded mode for stop checking, unlike StreamBufferWriter's clean downgrade to non-resumable (stream_buffer.py:64-151).
  • Silently truncated resume: an answer exceeding CHAT_STREAM_BUFFER_MAX_BYTES is marked truncated (stream_buffer.py:116-126) and a reconnecting client gets a partial answer with only a 'truncated' meta flag - acceptable-tail-truncation is a hidden, undeclared protocol decision.
  • Multi-model mainline ambiguity: all models share one mainline chain (process_message.py:1223-1226) but compression is claimed by the first non-errored persisting model measured against the min window across all turn models (compression_max_input_tokens=min(...), process_message.py:1288-1289) - one model's compression decision can destroy history another differently-windowed model needed, and which model's branch becomes canonical for the next turn is implicit rather than declared.
  • History overflow crash: negative budget raises ValueError (llm_loop.py:449-450) - a huge persona prompt plus project files on a small-window model becomes a failed request instead of an ordered eviction.
  • Citation-number namespace exhaustion: concurrent tools get +100 citation ranges (tool_runner.py) and cross-message replay replaces earlier tool bodies with placeholders; anything letting the model re-reference prior-turn documents collides with the 'results are no longer accessible' lie - an observable model-confusion mode.
  • Queue-type erosion: the merged queue element type already includes a bare object() sentinel (process_message.py:1204), inviting future contributors to leak untyped payloads through the public stream contract; the first bug on this path will be an untagged packet reaching the wire.
  • Persona drift via silent skips: personas built on MCP tools or credential-backed custom tools silently change capabilities with credential state (tool_constructor.py:169) - a reproducibility loss the runtime must surface instead of hide.
  • MCP/OAuth-dependent capability gaps reproduce at runtime: construct_tools silently drops unavailable tools (tool_constructor.py:255-257), so a deployed persona can behave differently from its declared tool list with no runtime signal of the gap.

Steal — essences for our portable runtime

  • The packet envelope: a fixed-size routing header (turn_index, block/tab index, model_index, sequence, kind) plus a small stable tagged-union of event payloads (start/delta/end/error/stop), as in emitter.py plus placement.py plus streaming_models.py. This is a ready-made C actor message schema - message passing with built-in communication visibility, and every conversation is one loggable, replayable event stream.
  • Durable append-only stream buffer with resume cursor (StreamBufferWriter essence, stream_buffer.py:64-151): compressed chunked appends on pluggable storage with a truncation flag, TTL, and failure-downgrades-to-non-resumable semantics. Maps directly to WaveDB as the actor's event log: treat the outbound stream as the persistence, not a cache afterthought.
  • The cancel fence, hardened: a small durable boolean in the store checked at quiescence points (chat/stop_signal_checker.py) - the right replacement for signal-based cancellation in C. Improve it by checking at deterministic boundaries (between cycles, before/after each tool) instead of a 50 ms wall-clock poll.
  • Budgeted moving-context layout as a named policy object: per-block token accounting (system, persona anchor, project files, history, reminder) with a defined eviction ORDER - history from the top, cross-turn tool bodies collapsed to args-plus-placeholder (README:78-87), forgotten-files notices to preserve addressability (llm_loop.py:~540) - and graceful degradation replacing the raise at llm_loop.py:449-450. The re-anchoring of durable persona instructions near end-of-context is the empirically justified heart (README:133-162) and should be a first-class, testable runtime feature.
  • Emitter/Collector actor shape: workers are pure packet producers accumulating state only; a single drain point owns ordering, cancellation, tee-to-log and persistence (emitter.py, _run_models). In C: worker actors never touch sockets or storage; one serializer actor per session does. The documented rule that emitters and state containers are accumulator-only (chat/README.md:197-212) is the actor discipline the C runtime should enforce structurally.
  • Exactly-once outcome persistence: idempotent persistence via claim flags (persisted[], the single compression_claimed latch, process_message.py:1221-1226 and 1241-1290). In a durable store this becomes a CAS-style claim record keyed by (session, turn, model) - the correctness mechanism survives crash/restart, which lock-based exactly-once does not.
  • Citation indirection: the LLM emits plain integer references; the runtime owns the number-to-document mapping, rewrites links in the live stream (DynamicCitationProcessor), and persists per-message citations. Worth generalizing into a runtime-level 'reference namespace' for any tool-produced artifact, not just documents.
  • LLM-facing error protocol: every internal failure renders as a typed, model-consumable message (tool_runner.py:147-229 always produces an llm_facing_response and SectionEnd) while the raw cause stays in logs. For a C runtime: a small closed set of tool-outcome statuses separated from internal error codes at the tool boundary.
  • Loadable persona essence distilled: Onyx's persona is a system prompt template plus placement mode plus tool manifest plus context-attachment policy plus compression parameters. A C runtime should centralize exactly this bundle into ONE serializable, loadable persona manifest instead of Onyx's scattered ORM rows plus isinstance code paths.

Steal-avoid / reject

  • The execution substrate: ThreadPoolExecutor plus threading.Lock plus closure-captured flags plus unbounded queues (process_message.py:1159-1240, chat_state.py:46). This shape exists to work around Python threads; a C actor runtime is the cure, not a port of the disease.
  • The ~2000-line procedural orchestration layer (process_message.py build_chat_turn/_stream_chat_turn/_run_models) and its flag-and-array bookkeeping: port the behavior contract, not the code.
  • LiteLLM, SQLAlchemy/FastAPI/Pydantic, the Vespa-backed RAG pipeline, connectors, SSO/tenancy machinery, and SearchTool's in-tool LLM query expansion (search_tool.py:600-660): product infrastructure, not harness essence. The runtime needs a tool ABI and a provider-agnostic streaming client interface, not a provider multiplexer.
  • isinstance-based prompt sections (prompt_utils.py:299-342) and behavior-name special cases such as STOPPING_TOOLS_NAMES at llm_loop.py:1451-1457: fold into the persona manifest's tool descriptors instead of type-switches scattered in prompt assembly.
  • Silent capability filtering in the tool constructor (tool_constructor.py:169, 255-257): replace with an explicit 'tool unavailable' event on the stream.
  • Magic protocol constants: the +100 citation ranges in tool_runner.py, FENCE_TTL = 600 s in stop_signal_checker.py:7, MAX_LLM_CYCLES = 6 from env in configs/chat_configs.py:12. Make them runtime/persona parameters with defined collision and expiry semantics.
  • The NDJSON-payload-over-SSE-framing mismatch (StreamingResponse with media_type text/event-stream carrying JSON lines): pick one real wire framing in the C runtime instead of inheriting the ambiguity.
  • Tenant isolation, Postgres schema routing, Redis key-prefix tenancy (stop_signal_checker.py:14-19) and the ORM Persona model with eager-loaded rows: replace with the single loadable persona record the C design already wants.

The essence here is excellent and directly on-target for a C actor runtime on WaveDB: a typed packet envelope with routing headers, an append-only durable stream log with cursor replay, a durable cancel fence, budgeted prompt assembly with a documented re-anchoring policy, a canonical-message/projection split, idempotent outcome persistence, and an LLM-facing error protocol. The realization is the opposite shape - threads, locks and closure-captured flags inside a ~2000-line procedural orchestrator - so treat Onyx as a design document that happens to be executable: steal the nine patterns above, port none of the mechanism. Its two weakest points, the drain-loop concurrency core and the unenforced prompt-layout invariants, are exactly the spots a message-passing C runtime should re-derive structurally.

Distinctive design facts

  • Loop exit is driven by whether any tool_use block arrived during streaming, not stop_reason — the comment says `stop_reason === 'tool_use' is unreliable -- it's not always set correctly. Set during streaming whenever a tool_use block arrives — the sole loop-exit signal` (src/query.ts:552-557; needsFollowUp set true at :834).
  • Tools can start executing before the model finishes streaming: streamingToolExecutor.addTool is called per tool_use block inside the streaming for-await, gated by config.gates.streamingToolExecution (src/query.ts:561,735,840-844; class at src/services/tools/StreamingToolExecutor.ts:40).
  • Tool calls are partitioned by tool.isConcurrencySafe: consecutive safe tools run concurrently (cap from CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY parsed at toolOrchestration.ts:10, default 10) while unsafe batches run serially (src/services/tools/toolOrchestration.ts:19-60).
  • The system prompt is a cache-stable array of sections closed by SYSTEM_PROMPT_DYNAMIC_BOUNDARY ('__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__', src/constants/prompts.ts:114-115, :573) with static content and registry-managed dynamic sections via systemPromptSection / DANGEROUS_uncachedSystemPromptSection (used at src/constants/prompts.ts:444-570) — engineered around prompt-cache prefix stability, mirroring the base/overlay split in toolToAPISchema (src/utils/api.ts:147-257).
  • The permission gate is a layered chain: rules/safety checks, then mode transforms (dontAsk ask->deny at permissions.ts:503-513; auto mode -> yoloClassifier with consecutive-denial tracking at :744-745), with tool-specific checkPermissions and hooks resolved in toolExecution.ts before tool.call (:921, :1207) and the interactive dialog (src/hooks/toolPermission/handlers/interactiveHandler.ts) as the fallback.
  • Subagents are recursive query() invocations with scoped state: runAgent.ts:748 passes its own system prompt, isolated caches, agent-id-scoped queue draining (query.ts:1574-1577 filters cmd.agentId === currentAgentId), and a sidechain transcript (recordSidechainTranscript, runAgent.ts:735,794); forkSubagent.ts makes subagent_type optional so omission triggers an implicit context-inheriting fork.
  • Stop hooks are part of termination: when the model returns without tool calls, handleStopHooks (src/query/stopHooks.ts:65) can return blockingErrors that re-enter the loop (stopHookActive: true, transition 'stop_hook_blocking' at src/query.ts:1300-1302), but stop hooks are deliberately skipped on API-error turns to avoid a death spiral (src/query.ts:1260-1265, with executeStopFailureHooks fired instead).
  • Dynamic context reaches the model as <system-reminder>-wrapped attachment user messages (memory hits, file-change notices, skill discovery, queued commands) generated per turn by getAttachmentMessages (src/utils/attachments.ts, consumed at src/query.ts:1580); messages.ts special-cases the '<system-reminder>' prefix when smooshing content blocks (src/utils/messages.ts:1791-1850).

Critique

Strengths

  • The turn loop is an explicit, inspectable state machine, not a call tree. State is one struct-shaped record with a named `transition` field ('Why the previous iteration continued. Undefined on first iteration. Lets tests assert recovery paths fired without inspecting message contents.' — src/query.ts:204-217). Every recovery path is a continue site that writes a whole new State record and names its reason: collapse_drain_retry (query.ts:1099-1115), reactive_compact_retry (:1152-1165), max_output_tokens_escalate (:1207-1220), max_output_tokens_recovery (:1231-1251), stop_hook_blocking (:1283-1305). For a C actor runtime this is exactly the shape you want: the durable record is the turn state, and 'transition reason' is the resume log.
  • Loop termination is decided by observed behavior, not a provider hint: 'stop_reason === tool_use is unreliable -- it is not always set correctly... the sole loop-exit signal' (src/query.ts:552-558, needsFollowUp set at :834, exit branch at :1062). This is a real correctness lesson for a port: trust what your own parser saw on the wire, and treat upstream status enums as advisory.
  • Tool concurrency policy is a genuinely portable, small kernel: consecutive concurrency-safe calls batch (env cap, default 10, toolOrchestration.ts:8-12), every unsafe call runs exclusively; and the classifier itself fails closed — `catch { return false }` when isConcurrencySafe throws (toolOrchestration.ts:99-108), mirrored in StreamingToolExecutor (src/services/tools/StreamingToolExecutor.ts:104-113). Three invariants, no actor framework needed: read-parallel, write-exclusive, conservative fallback.
  • Durability is treated as a first-class loop input, not an afterthought. The user message is persisted BEFORE the model call with an explicit rationale comment ('--resume fails... Writing now makes the transcript resumable from the point the user message was accepted, even if no API response ever arrives' — src/QueryEngine.ts:436-463), and writes flow through a per-file ordered queue with batched appends and backpressure-resolved flushes (src/utils/sessionStorage.ts:606-678). This is a WAL pattern in all but name and is the single best fit for a WaveDB-backed port: append-only, ordered, crash-tolerant.
  • The recovery ladder encodes hard-won spiral-avoidance rules as data rather than discipline: stop hooks are deliberately skipped on API-error turns ('error → hook blocking → retry → error → … the hook injects more tokens each cycle', query.ts:1258-1265), and the state comment documents a fixed infinite loop: 'Resetting to false here caused an infinite loop: compact → still too long → error → stop hook blocking → ... burning thousands of API calls' (query.ts:1292-1297). Single-shot flags (hasAttemptedReactiveCompact) and counted budgets (MAX_OUTPUT_TOKENS_RECOVERY_LIMIT, maxOutputTokensRecoveryCount) make termination an explicit, testable property of the loop.
  • Prompt-prefix handling is engineered for cache locality as a deliberate byte-stable discipline: an array-of-sections system prompt closed by SYSTEM_PROMPT_DYNAMIC_BOUNDARY (src/constants/prompts.ts:114-115, :573), a session-stable tool-schema cache behind toolToAPISchema (src/utils/api.ts:119, 147-257), and careful clone-not-mutate plumbing with the comment 'mutating it would break prompt caching (byte mismatch)' (query.ts:742-747). A C runtime gets this essentially free with a content-addressed store — the pattern (deterministic serialization of the prefix, append-only variation after a boundary) transfers directly to content-addressed WaveDB blocks.
  • Dynamic context uses one uniform channel: per-turn `<system-reminder>`-wrapped attachment user messages from getAttachmentMessages (src/query.ts:1580; src/utils/messages.ts:1791-1850 special-case the prefix), covering memory hits, queued commands, skill discovery. One message pipeline, greppable in the transcript — the right shape for an actor runtime where the store is also the log.

Weaknesses

  • queryLoop is a god function: 1729 lines (src/query.ts) with 7 distinct `state = next` continue sites, ~12 mutable State fields, PLUS loop-local mutable state deliberately kept off State — 'Loop-local (not on State) to avoid touching the 7 continue sites' (taskBudgetRemaining, query.ts:282-291). Truth is split across two scopes; every new recovery path must be threaded through all sites by hand. In C this becomes an unmaintainable switch; the fix is to make State itself the persisted record and drop the parallel variable.
  • The ToolUseContext is a god object, and it is the antithesis of the actor pattern: it carries file-state caches (readFileState, nestedMemoryAttachmentTriggers), a live abortController, getAppState/setAppState closures, analytics hooks, setInProgressToolUseIDs, and even UI concerns like setSDKStatus (see the construction at src/QueryEngine.ts:490-527). Spawning an isolate means cloning this whole bag createSubagentContext(toolUseContext, {...}) — src/tools/AgentTool/runAgent.ts:700-714. Shared mutable ambient context threaded by reference through every tool, permission check, and hook means 'isolated actors + message passing' never actually happens: parent and child contexts leak (shareSetAppState: !isAsync, runAgent.ts:709).
  • Ambient global state leaks into correctness-critical paths. The permission gate reads and writes process-wide appState (src/utils/permissions/permissions.ts:486-498) and needs a special-case `context.localDenialTracking ?? appState.denialTracking` because async subagents 'whose setAppState is a no-op' (permissions.ts:553-558). When part of your safety logic must be duplicated per-execution-context because the store is not actually shared, the storage architecture is wrong for isolation — a durable, addressable per-actor state (WaveDB-style) removes the special case.
  • Context management is four stacked mechanisms whose correctness depends on documented-seeming ordering contracts, each defended by comment: applyToolResultBudget must run before microcompact because cached MC 'operates purely by tool_use_id... content replacement is invisible to it' (query.ts:369-372); snipTokensFreed must be plumbed to autocompact because 'tokenCountWithEstimation alone can not see it' (query.ts:396-400); collapse must run before autocompact or 'autocompact... replaces granular context with a single summary' (query.ts:428-431). Two of the four (HISTORY_SNIP snipCompact, CONTEXT_COLLAPSE contextCollapse) are feature()-gated and their module files are ABSENT from this tree (query.ts:401, 440) — the shipped artifact relies on code it does not contain. This is emergent ordering dependency, not design; a portable runtime needs ONE boundary rule + ONE summarizer, not five cooperating mechanisms.
  • Tool execution has TWO parallel engines with subtly duplicated invariants: the batch path (partitionToolCalls in toolOrchestration.ts:91-116) and the streaming path (StreamingToolExecutor, class at :40) which re-implements the same safe/unsafe scheduling (canExecuteTool :129-135), plus its own lifecycle verbs — discard() for stream fallback (StreamingToolExecutor.ts:69-71), synthetic error messages for user_interrupted/sibling_error/streaming_fallback (:153-180). And it must be torn down and rebuilt mid-stream on fallback with tombstones for orphaned messages (query.ts:712-740). That entire subsystem is latency-driven accretion; in a message-passing C runtime, one executor with a start-message queue covers both.
  • Concurrency is bolted onto an ordered-yield generator rather than real isolation: parallel safe tools' contextModifiers are queued and replayed afterwards in block order (toolOrchestration.ts:31-63) — determinism is preserved only by the convention that modifiers are pure and deferred. Nothing enforces it; a tool whose modifier reads another tool's mutation gets whatever order yields happened to settle. Correctness depends on an implicit rule no type enforces.
  • Yield-based streaming couples four concerns through one generator type: protocol events, transcript records, UI progress, and analytics all ride StreamEvent|RequestStartEvent|Message|TombstoneMessage|ToolUseSummaryMessage (query.ts:221-227). Even subagent progress forwarding special-cases TTFT metrics inside the loop (runAgent.ts:759-768). In C this must be split into distinct channels (state transition log vs. observational progress) or consumers will have to pattern-match heterogeneous events forever.
  • Bridging fragile coupling: runTools looks up the assistant message with `assistantMessages.find(...)!.message.content.some(...)` per toolUse (toolOrchestration.ts:132-136 and :165-169) — a non-null assertion over a linear scan whose validity depends on the loop having pushed the message earlier; the same id-pairing logic is re-derived independently in StreamingToolExecutor. This id-correlation belongs in the runtime, not re-derived per engine.
  • Persistence lacks cross-stream ordering guarantees that the design quietly assumes: writeQueues is a Map keyed by file path with an independent 100ms flush timer per instance (sessionStorage.ts:561-632) and a 100MB MAX_CHUNK_BYTES batch — ordering between the main transcript and sidechain files is incidental. Fire-and-forget writes are also accepted at critical points ('fire-and-forget — persistence failure should not block the agent', runAgent.ts:732-742), so resume correctness is best-effort at the edges.
  • Host entanglement inside the loop: a dumpPromptsFetch closure is constructed per query specifically to cap memory at ~700KB because naively capturing request bodies costs '~500MB for long sessions' (query.ts:582-590); currentModel is recomputed from permissionMode including the plan-mode 200k heuristic inside the loop (query.ts:570-578). Scheduling and debug-capture policy live inside the turn engine instead of being capabilities passed in — in C these become actor config/permissions, not loop code.

Failure modes

  • Livelock/spiral in the recovery ladder: query.ts:1292-1297 documents a shipped infinite loop (compact → still-too-long → stop-hook blocking → compact, 'burning thousands of API calls') caused by resetting hasAttemptedReactiveCompact at a continue site; the fix is another hand-maintained conjunct. Every new recovery path re-opens this class of bug — 7 continue sites each recreate the full 12-field State by hand.
  • Nondeterministic tool-batch context: concurrent safe tools mutate ToolUseContext via deferred, order-replayed contextModifier functions (toolOrchestration.ts:31-63) — if two modifiers touch the same field, the batch order (and the model's block order) decides the winner; nothing enforces commutativity.
  • Tool-id coupling assertion: runToolsSerially/runToolsConcurrently do assistantMessages.find(msg => content.some(tu => tu.id === toolUse.id))! (toolOrchestration.ts:132-136, 165-169) — a non-null assertion on a linear array scan; any divergence between toolUseBlocks and assistantMessages (exactly what the fallback path perturbs) crashes the turn instead of degrading.
  • Transcript-loss edge cases: lastRecordedUuid tracking in runAgent.ts:744-745 and fire-and-forget recordSidechainTranscript (735) mean subagent transcript continuity is best-effort; a resume that lands mid-sidechain can drop the tail. The JSONL queue also silently swallows append errors (appendToFile catch at 634-643 retries mkdir but a second failure resolves the write as done).
  • Withheld-error loss window: comment at query.ts:621-625 — 'Withholding (inside the stream loop) and recovery (after) must agree; CACHED_MAY_BE_STALE can flip during the 5-30s stream, and withhold-without-recover would eat the message.' A feature flag flipping mid-stream can silently drop the model's error, acknowledged in-tree as a real hazard.
  • Prompt-cache corruption by mutation: byte-level invariants ('mutating it would break prompt caching (byte mismatch)', query.ts:745-746; clone-only-if-added-fields logic 771-777) are enforced by discipline in a 1729-line file, not by types — one refactor away from destroying cache locality (pure $ cost, no correctness signal).
  • Unverifiable feature surface: HISTORY_SNIP and CONTEXT_COLLAPSE modules are absent from this tree while query.ts branches on them (~15 call sites); a port could never confirm what snipCompactIfNeeded or recoverFromOverflow do — any 'steal' of the collapse design is guesswork.

Steal — essences for our portable runtime

  • Transition-record turn loop: the State + `transition` pattern (query.ts:204-217, 1099-1115, 1152-1165, 1283-1305). In C: a `turn_state` struct with a `reason` enum, one dispatch at the top of the loop, and the record appended to WaveDB each iteration. This is the single most portable idea in the codebase — it makes recovery, resumption, and post-hoc debugging all the same mechanism, and it maps 1:1 onto WaveDB records.
  • Durable-input-before-action: record the accepted user input durably before any model work (QueryEngine.ts:436-463), plus an ordered, batched, per-stream write path. Essence for WaveDB: every actor turn opens with a transaction containing {input, snapshot, plan-transition}; the loop is replayable from the store alone, and crash-resume is structural, not emergent.
  • Loop-exit by observed behavior, not provider metadata (query.ts:552-557). A C runtime actor loop should terminate/continue on whether tool invocations arrived (its own protocol), never on a carrier-supplied status field — this decouples the runtime from any vendor's reliability habits.
  • Read-parallel / write-exclusive scheduler (partitionToolCalls, StreamingToolExecutor.canExecuteTool). Three invariants, no dependencies: concurrency is data-driven (safe(derivedInput) → parallel; unsafe → exclusive), conservatively fall back to exclusive on classifier failure, and a per-subtree abort so one failure kills siblings without cancelling the turn. Direct fit for a C actor with a run-queue and per-actor abort flags.
  • Cache-stable deterministic prefix engineering (SYSTEM_PROMPT_DYNAMIC_BOUNDARY, static/dynamic section split, base/overlay schema cache). Essence: render the entire prompt prefix to a canonical, append-only, byte-stable buffer, content-address it (WaveDB is ideal for this — dedupe/cache by hash of prefix), and only vary the tail. This is a durability-and-cost pattern, not an API-specific trick.
  • Dynamic context as in-band tagged messages (attachments channel, system-reminder convention). Adopt as the runtime's second-class message kind: {attachment} messages carry memory, queue notifications, file changes — one transport, greppable in the waveform store, no second message pipeline to implement per platform.
  • Recovery as data with one-shot guards and stop-hooks-on-error suppression (query.ts:1062-1265). Port the invariant, not the four layers: a withheld error is a state record; each recovery kind fires at most once per turn (a guard bit in State); and user-defined hooks are never evaluated on failed turns. That single rule is what prevents runtime-burning loops.
  • Subagent as scoped re-entry of the same loop: same entry function, fresh actor id, own snapshot, own transcript stream, agent-id-scoped queue filtering (runAgent.ts:700-757; query.ts:1574-1577). In C actor terms, spawning an agent is literally spawn(actor, init_record) with parent-id for the progress channel — no special child-loop machinery at all.

The core is worth stealing and the periphery is not. queryLoop's state-machine-with-named-transitions, the behavior-driven loop-exit signal, the read-parallel/write-exclusive tool scheduler, the eager-WAL transcript, and the byte-stable prompt-prefix discipline are exactly the right essences for a C actor runtime over a durable store — most translate almost without change (transition records become WaveDB rows; the JSONL queue becomes the store's transaction log). But the executable substance around that core is an unportable TypeScript product: a 12-field ambient ToolUseContext instead of actor state, four mutually-coupled compaction mechanisms, a dual tool-execution engine, and UI/analytics/feature-flag entanglement throughout; it should be mined for patterns and abandoned wholesale as code — and as decompiled proprietary source it cannot be copied anyway.
